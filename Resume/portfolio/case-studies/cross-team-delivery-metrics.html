Making delivery metrics work across teams that work differently

Client Global engineering software company Role Reporting architect Scope Metrics design and automation

Problem

The organization wanted consistent delivery metrics across its engineering teams — sprint commitment, cycle time, release readiness, historical performance. Reasonable ask. The obstacle was subtle enough that it had gone unnoticed for a while.

Teams had customized their work-item workflows over years. The same state name meant different things depending on which team you asked. One team's "resolved" meant code complete and awaiting test. Another's meant tested and awaiting release. A third used it for something else entirely.

Any report keyed on state names produced numbers that looked authoritative and were quietly wrong. Two teams with identical output could appear wildly different, and leadership had no way to know which comparisons were meaningful.

The obvious fix — standardize workflows across all teams — was not viable. Those workflows reflected genuine differences in how teams operated, and forcing convergence would have created more disruption than the reporting was worth.

The reporting requirement and the autonomy requirement were both legitimate. The design problem was finding a layer where they did not conflict.

Approach

The resolution came from a platform detail: teams can define their own states, but every state must map to a fixed set of state categories. Teams control the names; the categories are constant.

  • Surfaced the ambiguity concretely with edge cases across several teams, so the group could see where existing reports diverged from reality.
  • Facilitated agreement to report on state categories rather than individual state names, preserving team-level workflow freedom.
  • Worked through the definitional cases that matter in practice: what counts as complete, how to treat work finished in development but awaiting downstream steps, and how items moved between sprints should be classified.
  • Proposed supplemental measures for work sitting in intermediate states, with a review threshold framed as a visual reference point rather than a target — deliberately, so an initial estimate would not harden into a de facto service level.

Solution

  • Reporting keyed on normalized state categories, giving organizationally consistent metrics while teams kept their own workflows.
  • A distinction between development-complete work and fully deployed work, with aging analysis for items waiting on build, test, or release.
  • Explicit rules for planned versus unplanned work, including items removed from a sprint and re-added late — treated as unplanned, since they were no longer part of the active commitment.
  • Automated ingestion from two work-tracking systems into Power BI, replacing manual PowerShell extraction that required regular intervention.

Outcome

  • Consistent metrics without forced standardization. The organization got comparable measures across teams while every team kept the workflow it needed.
  • Manual extraction eliminated. Script-based collection was replaced by automated reporting across both work-tracking systems.
  • Better questions became askable. Aging analysis on development-complete work surfaced bottlenecks between code complete and release that nobody had been measuring.
  • Definitions were documented and agreed. Metric meaning was settled explicitly rather than left to individual report authors.
